# 优眠小助手 v2.0 对接方案

> 目标：把当前演示版智能体接入真实店铺系统，支持物流实时查询、真实人工客服、商品知识库自动更新。

---

## 一、背景与问题

v1.0 的智能体运行在扣子平台上，能回答规则类问题，但离生产环境还有三个缺口：

| 缺口 | v1.0 现状 | 问题 |
|------|----------|------|
| 物流查询 | 知识库只能答"48小时内发货" | 无法回答"我的快递到哪了" |
| 人工客服 | 仅返回文案"回复转人工" | 没有真实的客服接管链路 |
| 知识库更新 | 手动上传 Markdown 文件 | 商品上下架/改价后知识库过期 |

**根因**：知识库是静态的，而这三类都是**动态数据**，必须通过接口实时获取。

---

## 二、整体架构

```
店铺顾客
   │  对话
   ▼
扣子智能体（人设 · 六路条件判断工作流 · 知识库）
   │  自定义插件调用（HTTPS）
   ▼
你的后端服务  ← 新增核心层（鉴权 · 数据加工 · 转发）
   │  接口调用
   ├──→ 店铺 ERP        商品 · 价格 · 库存
   ├──→ 物流查询 API     运单实时轨迹
   └──→ 人工客服系统     工单 · 会话转接
```

**为什么必须有后端服务**：
1. 平台密钥（ERP、物流 API）不能写在前端或扣子插件里，会泄露
2. 需要对多来源数据做聚合、脱敏、缓存
3. 扣子插件只负责"发请求 + 收结果"，业务逻辑放在后端

## 三、需求一：物流实时查询

### 3.1 链路

```
用户："我的快递到哪了？"
   → 工作流识别意图 = logistics_detail
   → 判断是否已拿到订单号
        ├─ 否 → 追问"请提供订单号或下单手机号"
        └─ 是 → 调用插件 queryLogistics
                 → 后端 /api/logistics
                 → 快递100 / 快递鸟 / 店铺ERP
                 → 返回运单轨迹
   → LLM 整理成客服话术返回
```

### 3.2 后端接口设计

```
POST /api/logistics
Request:
{
  "order_no": "202610100001",      // 订单号
  "phone_tail": "8888"             // 或手机号后四位（二选一）
}

Response:
{
  "code": 0,
  "data": {
    "carrier": "中通快递",
    "tracking_no": "ZT1234567890",
    "status": "运输中",
    "latest": "2026-10-10 14:20 快件已到达【上海转运中心】",
    "traces": [
      { "time": "2026-10-10 14:20", "desc": "快件已到达【上海转运中心】" },
      { "time": "2026-10-10 09:05", "desc": "快件已从【杭州分拨中心】发出" }
    ],
    "estimated": "预计 10-11 送达"
  }
}
```

### 3.3 扣子插件配置（OpenAPI 3.0）

```yaml
openapi: 3.0.0
info:
  title: 物流查询
  version: 1.0.0
servers:
  - url: https://your-backend.com
paths:
  /api/logistics:
    post:
      operationId: queryLogistics
      summary: 根据订单号查询物流实时轨迹
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              properties:
                order_no:
                  type: string
                  description: 订单号
                phone_tail:
                  type: string
                  description: 手机号后四位
      responses:
        '200':
          description: 查询成功
```

### 3.4 关键难点

- **身份识别**：用户不会主动说订单号 → 工作流里加"追问轮次"，最多追问 2 次
- **缓存**：同一订单 5 分钟内重复查询直接返回缓存，降低第三方 API 调用成本
- **降级**：第三方接口超时 → 返回"物流信息暂时查询不到，已为您转人工核实"

## 四、需求二：真实人工客服

扣子**不提供人工坐席**，必须对接外部客服系统。三种方案按成本递增：

### 方案 A：前端跳转（推荐先做）

最简单，不需要后端改动。

- 智能体识别"转人工" → 返回带动作标识的回复
- 前端页面捕获该标识 → 弹出跳转按钮 → 跳到店铺客服（微信客服 / 企业微信 / 第三方客服）

```
智能体回复：正在为您转接人工客服…
前端检测到 intent=transfer_human
   → 显示按钮「立即联系人工客服」
   → 点击跳转到 https://work.weixin.qq.com/xxx
```

### 方案 B：工单模式

- 插件调用 `POST /api/ticket` 创建工单
- 工单写入客服后台（企业微信/自建系统）
- 人工处理后将结果通过插件回写，用户下次进入会话时展示

```
POST /api/ticket
{
  "user_id": "u_123",
  "question": "我要投诉物流太慢",
  "contact": "138****8888",
  "conversation_id": "73xxxx"
}
```

### 方案 C：会话转接（体验最好，成本最高）

- 后端维护会话状态机：`bot → waiting_human → human → closed`
- 客服工作台实时订阅"待人工"会话，人工接管后消息不再经智能体
- 需要自建或用支持 API 的客服系统（如美洽、网易七鱼）

### 方案对比

| 维度 | A 跳转 | B 工单 | C 转接 |
|------|--------|--------|--------|
| 开发成本 | 低 | 中 | 高 |
| 用户体验 | 中（跳出去） | 中（异步） | 高（无缝） |
| 依赖 | 无 | 客服后台 | 自建客服台 |
| 建议 | ✅ 先做 | 二期 | 三期 |

## 五、需求三：商品知识库更新

### 方案对比

| 方案 | 数据来源 | 时效 | 成本 | 适用 |
|------|---------|------|------|------|
| A 定时同步 | 从 ERP 导出 → 调扣子 OpenAPI 更新知识库 | 分钟级（如每小时） | 低 | 材质、尺寸、卖点 |
| B 实时 API | 插件实时查商品接口 | 秒级 | 高（每次对话都调） | 价格、库存 |
| **C 混合（推荐）** | 稳定知识入知识库 + 动态数据走插件 | 兼顾 | 中 | 生产环境 |

### 5.1 定时同步实现（方案 A）

```
┌─ 定时任务（每天 03:00 / 每小时）
│   1. 从 ERP 拉取商品全量数据（SQL / OpenAPI）
│   2. 渲染成 Markdown 文档（含材质/尺寸/款式说明）
│   3. 调用扣子 OpenAPI 更新知识库文档
│   4. 触发知识库重新索引
└─ 失败重试 + 告警（企业微信机器人）
```

伪代码：

```python
# sync_products.py（示意）
import requests

def fetch_products_from_erp():
    """从店铺 ERP 拉取商品数据"""
    resp = requests.get(f"{ERP_BASE}/api/products", headers=ERP_HEADERS)
    return resp.json()["data"]

def render_markdown(products):
    """渲染为知识库 Markdown"""
    lines = ["# 优眠商品目录", ""]
    for p in products:
        lines.append(f"## {p['name']}")
        lines.append(f"- 参考价：{p['price']} 元")
        lines.append(f"- 材质：{p['material']}")
        lines.append(f"- 可选颜色：{'、'.join(p['colors'])}")
        lines.append("")
    return "\n".join(lines)

def update_coze_kb(content):
    """调用扣子 API 更新知识库文档"""
    return requests.post(
        f"{COZE_BASE}/v1/knowledge/document/update",
        headers={"Authorization": f"Bearer {COZE_TOKEN}"},
        json={"document_id": KB_DOC_ID, "content": content},
    )
```

### 5.2 动态数据走插件（方案 C）

价格、库存实时性要求高，走插件查询：

```
POST /api/product/price
{ "product_id": "P001" }
→ { "price": 299, "stock": 128, "promo": "满299减40" }
```

工作流里"商品咨询分支"调整逻辑：
1. 商品**说明类**问题（材质、洗护）→ 查知识库
2. 商品**价格/库存类**问题 → 调插件实时查

## 六、后端服务设计

### 6.1 技术选型建议

| 项 | 建议 | 说明 |
|----|------|------|
| 语言 | Python (FastAPI) 或 Node.js (Express) | 生态成熟、上手快 |
| 部署 | 云服务器 / 容器（Docker） | 需公网 HTTPS，扣子插件才能访问 |
| 鉴权 | 插件侧校验固定 Header | 防止接口被随意调用 |
| 缓存 | Redis / 内存缓存 | 降低第三方 API 成本 |
| 日志 | 结构化日志 + 告警 | 便于排查 |

### 6.2 接口清单

| 接口 | 方法 | 用途 |
|------|------|------|
| `/api/logistics` | POST | 物流实时查询 |
| `/api/ticket` | POST | 创建人工工单 |
| `/api/product/price` | POST | 实时价格/库存查询 |
| `/api/health` | GET | 健康检查（扣子插件连通性测试） |

### 6.3 安全要点

- 插件请求带签名或固定密钥 Header，后端校验来源
- 用户手机号、地址等敏感字段**脱敏**后再返回给智能体
- 接口限流，防止刷量
- 扣子侧令牌使用最小权限原则，不用时及时吊销

## 七、用户身份打通

三个需求都依赖"知道这个用户是谁"。三种方式：

| 方式 | 实现 | 体验 |
|------|------|------|
| 追问式 | 工作流里追问订单号/手机号后四位 | 可用，但多一轮 |
| 会话绑定 | 前端登录后把用户 ID 传给 SDK，后端按 user_id 查订单 | 好 |
| 免登打通 | 从店铺域名进入，带登录 Cookie/Token | 最好，需同域部署 |

**建议**：v2.0 先用"追问式"跑通链路，v2.1 再做免登打通。

## 八、落地优先级与里程碑

| 阶段 | 内容 | 依赖 |
|------|------|------|
| M1 | 商品知识库定时同步（方案 A） | 一个同步脚本 + 扣子知识库 API |
| M2 | 物流实时查询（插件 + 后端） | 后端服务 + 快递查询 API |
| M3 | 人工客服（方案 A 前端跳转） | 店铺客服系统链接 |
| M4 | 混合知识库 + 实时价格插件 | M1 + M2 经验 |
| M5 | 人工客服升级为工单/会话转接 | 客服后台 API |

## 九、风险与备选

| 风险 | 影响 | 应对 |
|------|------|------|
| 第三方物流 API 不稳定 | 查询失败 | 多源兜底 + 缓存 + 转人工 |
| ERP 无开放接口 | 无法自动同步 | 用数据库直连或导出文件定时解析 |
| 扣子插件调用超时 | 智能体无响应 | 设置超时 + 降级话术 |
| 密钥泄露 | 资产损失 | 密钥放后端、最小权限、定期轮换 |
| 成本超预算 | 积分/API 费用高 | 缓存、限流、知识库与插件分工 |

## 十、与 v1.0 的关系

v1.0 已完成的部分（人设、六路工作流、知识库、前端、发布上线）**全部复用**，v2.0 只做增量：

- 新增后端服务（独立仓库或本仓库子目录）
- 新增扣子自定义插件（3 个）
- 工作流里新增分支逻辑（物流明细、实时价格）
- 知识库从"手动上传"改为"自动同步"

**演进原则**：先跑通链路，再优化体验；动态数据走接口，静态知识进知识库。
