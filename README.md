## 功能

- **意图识别分流**：意图识别节点先把问题分到商品参数/退换售后/物流发货/团购定制/其他意图五类，由对应检索节点作答；五段提示词共用同一份公共基座，仅追加各自分类规则
- **知识库问答（RAG）**：基于 14 个上传文件、197 条问答（按 `###` 条目统计）与 21 个商品条目（按事实索引 `products` 统计）检索回答
- **一致性优先**：所有业务轮次统一走扣子，线上回复与智能体原话口径一致；本地确定性查表层、FAQ 首问缓存、数值守卫**默认关闭**（代码与开关保留，可用环境变量开回），本地只保留两件必要的兜底——空回复/裸标记兜底（避免白屏）与 `[[NO_ANSWER]]` 类标记替换成转人工话术。代价是原先秒回的事实题也要等模型，线上延迟明显变长
- **多轮上下文追问**：五个检索节点各自开启「会话历史」5 轮；智能体「对话设置」的携带上下文轮数 10 是总闸，但需节点输入模块引用「智能体对话历史」参数才生效，指代句/省略句（「那纯棉的呢」「能叠加吗」）可正确续答
- **分级消息处理**：问候语/转人工/结束语直接回复，业务咨询走对话流，异常走安全兜底
- **安全兜底**：无法回答时礼貌引导转人工，不编造答案、不冒充人工客服
- **可在线试用**：经后端代理与真实智能体流式对话，前端不暴露任何密钥
- **可量化评测**：31 条单轮 + 5 组多轮 + 12 条事实 + 6 条安全，按版本归档；当前关键信息覆盖率 100%、回复规范性 100%、事实 12/12、安全 6/6

## 对话流架构

```
用户输入（USER_INPUT / CONVERSATION_NAME）
   │
   ▼
意图识别（五类：商品参数 / 退换售后 / 物流发货 / 团购定制 / 其他意图）
   │
   ├─ 检索-商品参数 ┐
   ├─ 检索-退换售后 ┤
   ├─ 检索-物流发货 ┼→ 变量聚合
   ├─ 检索-团购定制 ┤
   └─ 其他意图     ┘
        · 五段提示词 = 同一份公共基座 + 各自分类规则
        · 技能：FAQ + 商品目录
        · 会话历史：开启（5 轮）
        · 事实口径速查块：发货 48h、非偏远地区无门槛包邮、签收起算、枕芯不支持等
   │
   ▼
结束节点（返回文本 {{reply}}，流式输出开启）
```

> 上述为扣子侧拓扑；请求先经后端，但业务轮次一律转发本对话流（一致性优先），本地只在空回复/裸标记时兜底。确定性查表层仍在仓库里，默认关闭，可用 `FACT_ANSWER_ENABLED=1` 开回直返。

> v1.x 是「意图识别（选择器）→ 六路 LLM → 代码节点聚合 → 结束」，代码节点收齐六路输出才能计算，回复整段一次性返回、无法流式；v2.0 曾合并为单节点并让结束节点直连 LLM 以满足流式条件。**当前方案 B** 在此基础上前置意图识别、把生成拆回五个检索节点，再用变量聚合汇总，五段提示词共用一份公共基座。

> **v2.0 起结束节点改用「返回文本 + `{{reply}}`」并开流式**：v1.9 的「返回变量」会把输出包成 `{"reply": ..., "branch": ...}`，代理必须收齐 JSON 才能拆，流式因此失效；`branch` 也随代码节点一起移除，改由后端按关键词推断后通过独立 SSE 事件下发（仅供日志与统计，不再作为路由能力的证据）。

**为什么用对话流**：客服是典型多轮场景，对话流绑定会话后可读历史消息，且发布渠道更广（API&SDK、小程序、社交渠道等）。工作流与对话流可一键互转。注意「会话记忆」分两层：智能体「对话设置」的携带上下文轮数（本项目 10）是总闸，但**只有大模型节点的输入模块引用「智能体对话历史」参数时才生效**；节点自己的「会话历史」开关与轮数是另一层（本项目五个检索节点均已开启，3 → 5）。哪一层实际生效取决于节点有没有引用该参数，以平台实际行为为准，不要简单断言取小值。此前 7 个节点全关，导致多轮追问断裂，v1.7 已全部打开。

**智能体接入方式**：采用「单 Agent（对话流模式）」，每轮对话直接执行绑定的对话流，省去规划层，响应更快；v2.0 起结束节点用「返回文本 + `{{reply}}`」直接输出纯文本并开启流式，`branch` 由后端按关键词推断，仅用于日志与统计。

## 技术栈

- 平台：扣子 Coze（www.coze.cn）
- 对话流：意图识别 + 五个检索 LLM 节点（五段提示词共用公共基座）+ 变量聚合 + 结束节点（返回文本，流式输出）
- 知识库：扣子平台自带的知识库检索（文本知识库，按需调用）；检索参数在扣子控制台配置；仓库侧另有一份从上传 md 生成的结构化事实索引（`data/kb_fact_index.json`），默认只用于空回复兜底（`FACT_ANSWER_ENABLED=1` 可开回确定性直答），仍无自建 embedding、向量库或重排
- 模型：豆包 2.0 pro
- 前端：HTML / CSS / JavaScript
- 后端：Python 3 标准库（`http.server` + `urllib`，零第三方依赖）；`kb_fact_answer.py`（确定性查表）与 `kb_numeric_guard.py`（数值守卫）保留，但默认关闭
- 部署：GitHub Pages（静态演示）+ 任意 Python 托管平台（真实对话）

## 本地运行（真实对话）

前端不保存任何令牌；令牌只存在服务端 `.env` 里，由后端代理转发请求。

```bash
# 1. 配置令牌（pat_ 开头，需勾选 Chat 权限）
cp .env.example .env        # 然后编辑 .env，填入 COZE_API_TOKEN

# 2. 启动服务（零第三方依赖，只用 Python 标准库）
python3 server.py

# 3. 打开页面（macOS 用 open；Windows 用 start；Linux 用 xdg-open）
open http://localhost:3000       # macOS
# start http://localhost:3000    # Windows
# xdg-open http://localhost:3000 # Linux
```

`server.py` 承担三件事：托管静态页面、提供 `POST /api/chat`（业务轮次一律流式转发扣子）、对上游空回复与标记做兜底替换。
另有 `POST /api/reset`：清空当前会话（丢弃 `conversation_id` 并让会话世代 +1），供页面右上角「清空对话」使用。
`GET /api/health` 单独限流（默认单 IP 每分钟 120 次），不占提问额度，供前端重连与后续定时探活使用。
页面加载时会探测 `/api/health`——探测成功走真实对话，失败（例如部署在 GitHub Pages）则自动降级为内置模拟回复的界面演示。

### 为什么需要后端代理

扣子 API 调用需要携带个人访问令牌（PAT）。如果把令牌写进网页源码，任何访客打开开发者工具都能抄走，
等于把账号交出去。所以令牌只放在服务端，浏览器只与本服务通信。

> 想让别人在线试用，把本仓库部署到任意支持 Python 的托管平台（如 Render / Railway / Fly.io），
> 在平台的环境变量中配置 `COZE_API_TOKEN` 即可。GitHub Pages 只能托管静态文件，跑不了后端。

### 可配置环境变量

所有参数都有默认值，通常只需填 `COZE_API_TOKEN`。需要调参时覆盖即可：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `COZE_API_TOKEN` | （空） | 扣子个人访问令牌，必填 |

| `MAX_MESSAGE_CHARS` | `2000` | 单条消息最大字符数；上线建议 `500` |
| `IP_PER_MINUTE` | `60` | 单 IP 每分钟提问上限；上线建议 `6` |
| `IP_PER_DAY` | `2000` | 单 IP 每天提问上限；上线建议 `60` |
| `GLOBAL_PER_DAY` | `5000` | 全站每日提问总量上限（兜底止损）；上线建议 `500` |

| `FACT_ANSWER_ENABLED` | `0` | 默认关闭；设 `1` 恢复事实索引命中直返（会绕开扣子，口径与智能体原话不一致） |
| `FACT_FALLBACK_ENABLED` | `1` | 空回复/裸标记兜底，必须保留（否则用户看到白屏）；设 `0` 关闭 |
| `NUMERIC_GUARD_ENABLED` | `0` | 默认关闭；设 `1` 恢复数值守卫（守卫会把原话整段替换成兜底话术） |
| `FAQ_CACHE_ENABLED` | `0` | 默认关闭；设 `1` 恢复 FAQ 首问缓存（同问题回放旧答复，口径可能与扣子不一致） |
| `ALLOWED_ORIGINS` | （空） | 额外允许的来源域名，逗号分隔 |
| `COZE_CA_BUNDLE` | （空） | 自定义 CA 证书路径；本地证书校验失败（certificate verify failed）时手动指定 |
| `COOKIE_SECURE` | （空） | 强制给会话 Cookie 加 `Secure`（`1`/`true`/`yes`）；留空则按请求的 `X-Forwarded-Proto` 自动判断（HTTPS 部署自动加，本地不加） |
| `HANDOFF_CONTEXT_ROUNDS` | `5` | 转人工时随接管队列保留的上下文轮数（最近 N 组问答） |

1. 把本仓库推送到 GitHub（`.env` 已被 `.gitignore` 忽略，不会被提交）

6. 得到形如 `https://youmian-customer-service.onrender.com` 的地址——把它发给别人即可直接对话

注意事项：

- **自动部署**：仓库已连接 Render 的 GitHub App，向 `main` 分支推送后会自动构建并部署（约 40–60 秒）
- **免费版会休眠**：15 分钟无访问后实例休眠，下次访问需要约 1 分钟唤醒。面试前先自己打开预热一次

- **令牌安全**：只填在 Render 控制台的 Environment 里，永远不要写进代码或提交到仓库

### 部署后自检

打开 `https://你的域名/api/health`，应返回：

```json
{"ok": true, "bot_id": "7706539492081270810", "api_base": "https://api.coze.cn", "token_ready": true, "version": "YoumianProxy/2.0.4", "uptime": 3600.0, "last_activity_at": "2026-11-13T08:05:00Z", "seconds_since_activity": 42.3, "keepalive_window_s": 1200, "keepalive_ok": true}
```

`token_ready` 为 `false` 说明环境变量没配上；`version` 可以用来确认这次部署的代码是否真的上线；`ok` 都拿不到说明服务没起来。
判读是否被唤醒过要看 `uptime`：免费实例休眠后进程会重建，`uptime` 归零重新计时，所以**隔几分钟连查两次、`uptime` 持续增长**才说明实例一直醒着；`uptime` 总是很小的值，就是还在反复冷启动。`keepalive_ok` 只反映「最近 20 分钟有没有真实流量」，外部探活没配或 GitHub 定时任务被降频时它会一直是 `false`，不能单独拿它判断线上是否可用，排查见 [`docs/keepalive.md`](docs/keepalive.md)。

**运行方式**：

```bash
python3 server.py                      # 终端 1：启动代理
python3 eval/run_eval.py               # 终端 2：跑 31 条单轮用例 → eval/report.md
```

支持 `--limit N`（只跑前 N 条/组）、`--workers N`（并发数）、`--base URL`（指向线上地址）三个参数；多轮模式下 `--workers` 不生效，因为同一组两句必须串行。
